# Phase 2 구조·성능 결과

기준: `336abd42e9a5b3e777faf2c7673a9c3f46e4ffa7`. Phase 1 테스트가 통과한 뒤 작업했습니다.

## A. 변경과 이유

- `components/map/SmokingZonesMap.native.tsx`: 지도 위치 구독과 Supabase 채널을 실제 `useEffect` 정리 함수에서 해제합니다. 비동기 시작 중 화면을 떠나도 뒤늦게 생긴 구독을 제거합니다. 콜백은 최신 region, zones, 자동 기록 설정, `addEntry`를 읽습니다.
- `components/StayMap.*`, `app/(tabs)/dashboard.tsx`, `app/(tabs)/map.tsx`: 네이티브 지도 import를 라우트 루트 밖의 플랫폼 파일로 분리했습니다. 웹 지도 화면은 작동하지 않는 등록 버튼 대신 지원 범위를 표시합니다.
- `components/history/BarChart.tsx`, `components/settings/SettingsParts.tsx`, `lib/goalTemplates.ts`, `lib/remoteRecords.ts`: 차트, 설정 공통 UI, 목표 템플릿, 원격 레코드 변환을 화면과 DataContext에서 분리했습니다. 기록 집계는 `lib/recordMetrics.ts`와 `lib/historyMetrics.ts`에 있습니다.
- `app/(tabs)/history.tsx`: 하루별 합계를 화면 렌더 중 한 번 계산해 선택일, 격려 문구, 차트 표시에서 재사용합니다.
- `app/(tabs)/goals.tsx`: 저장 모델에 기준값/일정이 없어 계산 불가능한 템플릿이 선택 화면에 나타나던 문제를 고쳤습니다. 기존 저장 목표는 유지하고 수동 진행으로 표시합니다.
- `components/app/`, `components/LoginScreen.tsx`, `components/components/LoginScreen.tsx`: 라우트 루트와 전체 참조 검색에서 실행 경로가 없음을 확인하고 별도 정리 커밋으로 삭제합니다. `components/contexts/DataContext.tsx`는 유지합니다.

## B. 호환성과 롤백

저장 키, Supabase 필드, 목표/기록 JSON 형식은 바꾸지 않았습니다. 지도 위치 감지의 정확도·거리·시간 조건과 자동 기록 조건도 유지했습니다. 해당 커밋을 역순으로 되돌릴 수 있으나 웹 번들 수정을 되돌리면 웹 export 실패가 돌아옵니다. 기존 로컬 데이터는 삭제하지 않았습니다.

목표 목록은 누적 목표 수가 늘 수 있지만 현재 실사용 길이 분포가 없어 가상화 효과를 측정하지 못했습니다. 히스토리 화면은 기록 전체를 행 목록으로 렌더하지 않고 차트·캘린더를 표시합니다. 기기에서 100/1000개 목표와 1만 건 기록을 넣어 스크롤 및 렌더 시간을 측정한 뒤 목록 가상화를 판단합니다.

## E. Claude 리뷰

Codex 작업 환경에서는 Claude를 호출할 수 없어, Claude Code(Opus 5.5)에서 기준 `336abd4`부터 `4004547`까지의 diff를 따로 리뷰했습니다. 대상은 `DataContext`, `syncPolicy`, `AuthContext`, `LocationStayContext`, 지도 네이티브 컴포넌트, `recordMetrics`입니다. 아래 두 건은 실제 버그로 확인해 수정했습니다. 나머지는 기록만 하고 코드는 바꾸지 않았습니다.

| 지적 | 판정 | 조치 |
| --- | --- | --- |
| 체류 자동 기록 폴링이 `[]` 의존성으로 **첫 렌더의 `addEntry`**를 캡처합니다. 그 시점에는 데이터 범위가 로드되지 않아 `saveLocal`이 항상 `Data is still loading`을 던집니다. 대기값은 그 전에 0으로 바뀌므로, 백그라운드 자동 기록은 저장 실패 시가 아니라 **항상** 유실되었습니다. | 확인(재현은 정적 분석) | `a125aff`: ref로 최신 `addEntry`를 사용합니다. 저장에 성공한 뒤에만 기록한 양을 차감하고, 기록 중 백그라운드가 더한 값은 보존합니다. 중복 flush를 막고 `lib/stayPendingCount.ts`에 테스트 5개를 추가했습니다. 키와 값 형식이 같아 마이그레이션은 필요 없습니다. |
| 계정 전환 시 새 계정의 로컬 JSON을 읽지 못하면 `finally`에서 범위가 로드된 것으로 표시됩니다. 이때 `snapshotRef`에는 이전 계정 스냅샷이 남아 있어, 자동 동기화가 이전 계정 기록과 대기 변경을 새 계정 키에 덮어쓰고 새 `user_id`로 업로드합니다. | 확인(테스트 재현) | `898edf3`: 로드를 시작할 때 스냅샷을 비웁니다. 로드에 실패한 범위는 미로드로 남겨 쓰기와 동기화를 차단하므로, 읽지 못한 저장값은 덮어쓰이지 않습니다. 회귀 테스트를 추가했습니다. |
| 지도 자동 기록 실패 시 `counted: false`로 되돌리지만, 분기 조건이 `!notified3min`이라 같은 체류에서는 재시도되지 않습니다. 표시된 오류도 다음 구역 조회가 성공하면 지워집니다. | 경미 | 유지합니다. 재시도 폭주와 중복 기록이 없는 쪽이 안전하므로 Phase 3 UX에서 오류 표시 방식을 정합니다. |
| 계정 삭제가 성공해도 기기의 계정별 스냅샷 키(`accountDataKey`)는 남습니다. | 개인정보, 정책 필요 | 삭제 범위(로컬 보존 여부)를 정한 뒤 처리합니다. |
| `reconcileRemote`는 서버에서 삭제된 행과 동기화되지 않은 기존 행을 구분하지 못해 매 동기화마다 충돌로 표시합니다. | 설계상 보수적 동작 | 서버 계약의 삭제 표식(tombstone) 결정 후 처리합니다. |

## F. 남은 위험과 다음 단계

실기기에서 지도 정리, 중복 백그라운드 태스크, 폴링, 배터리, 자동 기록 오탐을 검증해야 합니다. 체류 자동 기록의 `stay_monitor_pending_count`는 여전히 계정 구분이 없는 전역 키입니다. 귀속 규칙은 "flush 시점에 로드된 계정(비로그인이면 게스트)"으로 정했습니다. 앱이 종료된 동안 쌓인 값은 다음 실행 때 로그인한 계정에 기록되며, 계정 A에서 쌓인 값이 5초 폴링 전에 B로 전환되면 B에 기록될 수 있습니다. 계정별 키가 필요하면 백그라운드 태스크가 계정 ID를 읽을 수 있도록 저장 방식을 바꿔야 합니다. 차감 쓰기만 실패하면 다음 flush에서 중복 기록될 수 있으며, 유실보다 중복을 택했습니다. 백그라운드 태스크와 전경 flush의 읽기-쓰기 경합도 기기에서 확인해야 합니다. `DataContext`의 저장·동기화 오케스트레이션과 화면별 큰 JSX는 여전히 추가 분리 후보입니다. 동적 import를 포함한 의존성은 실제 사용 여부가 확실하지 않아 삭제하지 않았습니다. 정적 검사와 번들 게이트가 통과해 Phase 3의 **제안 작성**에는 진입할 수 있습니다. 측정 없는 위치 주기 변경과 대규모 화면 재작성은 진행하지 않습니다.
