# 서버 확인 및 변경 제안 (미적용)

저장소에는 Supabase SQL 스키마, RLS 정책, `delete-user` Edge Function 소스가 없습니다. 아래는 앱 코드의 호출에서 필요한 조건을 정리한 것이며 현재 서버에 존재한다고 가정하지 않습니다. 원격 DB 데이터나 프로덕션 설정은 변경하지 않았습니다.

## 먼저 확인할 항목

1. `entries`, `goals`, `profiles`, `triggers`, `smoking_zones`의 실제 컬럼·타입·기본키·인덱스와 외래키를 읽기 전용으로 확인합니다. 앱은 `entries.id`와 `goals.id`를 문자열로 보내며 `user_id`로 조회합니다.
2. 각 테이블의 SELECT/INSERT/UPDATE/DELETE RLS를 로그인 사용자 및 다른 사용자 두 계정으로 검증합니다. `smoking_zones`의 작성자와 `triggers`의 권한도 확인합니다.
3. `entries`와 `goals`의 `(user_id,id)` 유일성이 보장되는지 확인합니다. 현재 클라이언트 재시도는 같은 ID의 upsert를 사용하며 이 조건이 없으면 중복 방지가 검증되지 않습니다.
4. 백업·복구 절차와 테스트 환경을 확보한 후에만 스키마/함수 변경안을 실행합니다.

## 동기화 규칙

- UTC ISO 시각은 기록의 발생 시각으로 저장합니다. 달력·목표·통계는 기기의 현지 날짜로 계산합니다.
- 새 계정별 로컬 데이터는 `@SmokeTracker:account:<encoded user id>:data:v1`에 `{entries, goals, pending, legacyImported}`로 보존합니다. 기존 `@SmokeTracker:entries`와 `@SmokeTracker:goals`는 삭제하거나 자동 귀속하지 않습니다. 사용자가 설정에서 계정을 확인하고 복사할 수 있습니다.
- 로컬 변경은 먼저 저장하고 같은 ID의 대기 작업을 남깁니다. 원격 쓰기가 성공하면 작업을 제거합니다. 실패 시 작업과 로컬 데이터가 남으며 앱 시작 시 조회/재시도하거나 배너에서 수동 재시도합니다.
- 원격에만 있는 행은 수용합니다. 로컬에만 있거나 같은 ID의 내용이 다르면 로컬을 보존하고 충돌을 표시합니다. 원격 내용을 자동으로 덮어쓰거나 삭제를 자동 복원하지 않습니다. 대기 삭제는 tombstone으로 남깁니다.
- 현재 스키마에는 버전·수정 시각·삭제 tombstone이 확인되지 않아 서버와의 순서를 판정하거나 충돌을 자동 해결할 수 없습니다. 이를 위해 서버 측 `updated_at`/버전, 삭제 이벤트, 조건부 쓰기 또는 RPC를 별도 설계해야 합니다. 두 기기의 동시 편집·삭제와 오프라인 재연결을 테스트한 후 적용합니다.

## 계정 삭제 함수의 필수 계약

클라이언트는 `delete-user` 호출이 오류 없이 끝나고 `{ "deleted": true, "userId": "<현재 auth 사용자 ID>" }`를 반환할 때만 삭제를 확인합니다. 함수는 서버에서 호출자의 인증을 확인하고 관련 행과 인증 사용자를 일관되게 삭제해야 합니다. 실패·부분 실패·불명확한 응답은 성공으로 취급하지 않습니다. 현재 함수의 존재나 계약은 확인되지 않았으므로 실제 서버 확인 전에는 앱에서 계정 삭제가 완료되지 않을 수 있습니다. 함수 구현과 검증은 별도 서버 변경 제안으로 취급합니다.

## 검증 조건

- 두 테스트 계정이 상대 계정의 행을 읽거나 변경할 수 없어야 합니다.
- 동일 작업을 두 번 보내도 기록이 중복되지 않아야 합니다.
- 네트워크 중단, RLS 거부, 서버 오류 후 로컬 기록과 대기 작업이 유지되고, 재연결 후 같은 ID로 재시도되어야 합니다.
- 충돌은 양쪽 원본을 보존하고 사용자에게 표시되어야 합니다. 서버 버전 기능이 마련되기 전에는 자동 해결을 추가하지 않습니다.
- 계정 삭제 함수 오류·부분 실패·잘못된 `userId` 응답에서는 성공 화면과 로그아웃이 발생하지 않아야 합니다.
