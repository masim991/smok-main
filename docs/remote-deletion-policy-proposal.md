# 원격 기록 삭제와 오프라인 동기화 정책 제안

이 문서는 서버 스키마·RLS·Edge Function이 저장소에 없는 상태에서의 설계안입니다. SQL 적용, 원격 데이터 삭제, 배포는 수행하지 않았습니다.

## 현재 동작과 결정된 범위

- 사용자가 계정을 삭제하고 서버의 `{ deleted: true, userId }` 확인을 받아도 **해당 계정의 기기 스냅샷은 보존**합니다. 기존 게스트 기록과 다른 계정 기록도 유지합니다. 이것은 사용자가 선택한 정책이며 계정 삭제 화면의 설명과 확인 문구에 반영했습니다.
- 현재 원격 조회에서 같은 ID가 없으면 앱은 로컬 기록을 보존하고 충돌을 표시합니다. 원격 삭제와 아직 업로드되지 않은 로컬 기록을 구별할 자료가 없으므로 자동 삭제·복원은 하지 않습니다.
- 미동기화 로컬 변경은 같은 기록 ID로 재시도합니다. 원격과 내용이 다를 때는 자동 덮어쓰기를 중단합니다.

## 권장 정책: 서버 삭제 표식과 버전

1. 서버의 `entries`·`goals`마다 계정별 고유 ID, 단조 증가하는 `revision`, `updated_at`, `deleted_at`을 정의합니다. 실제 컬럼과 제약은 현행 스키마를 확인한 뒤 결정합니다. 물리 삭제 대신 삭제 표식을 일정 기간 보존해야 오프라인 기기에 삭제 사실을 전달할 수 있습니다.
2. 클라이언트는 마지막으로 확인한 서버 `revision`을 계정별 스냅샷에 추가하되, 기존 키와 레코드 형식은 그대로 읽을 수 있어야 합니다. 기존 스냅샷은 revision이 없는 상태로 처리하고 자동 서버 삭제 판단을 하지 않습니다.
3. 쓰기는 `baseRevision`과 안정적인 `mutationId`를 포함한 조건부 RPC 또는 동등한 서버 트랜잭션으로 처리합니다. 같은 mutationId 재시도는 한 번만 반영하고, 버전이 다르면 충돌 응답과 현재 서버 값을 돌려줍니다. 단순 `upsert`로 충돌을 해결하지 않습니다.
4. 서버 삭제 표식을 받은 기기에서 로컬에 대기 변경이 없고 로컬 revision이 일치하면 삭제 사실을 반영합니다. 대기 변경 또는 버전 불일치가 있으면 로컬 사본을 보존하고 사용자에게 **서버 삭제 수용 / 로컬 사본을 새 기록으로 복원**을 선택하게 합니다. 복원은 새 ID로 생성해 삭제된 ID를 되살리는 모호성을 없앱니다.
5. 기록별 충돌은 사용자가 해결할 때까지 유지합니다. 배너에는 충돌 건수와 관리 화면 진입을 제공하고, 동일 오류를 매번 새 알림으로 띄우지 않습니다.

## 적용 전 확인 조건

- 실제 `entries`·`goals` 스키마, FK, RLS의 SELECT/INSERT/UPDATE/DELETE 범위, 계정 삭제 함수의 데이터 삭제 범위를 확보합니다. 다른 계정의 행·삭제 표식·버전은 조회하거나 변경할 수 없어야 합니다.
- 기존 행에 revision을 부여하는 마이그레이션과 롤백·백업 절차를 테스트 환경에서 검증합니다. 구버전 클라이언트의 `upsert`가 새 버전 정책을 우회하지 않도록 서버 호환성을 확인합니다.
- 두 기기 동시 수정, 한 기기 오프라인 삭제, 재설치, 중복 mutationId, 네트워크 응답 유실, RLS 거부, 계정 전환, 오래된 삭제 표식 만료를 자동 테스트와 Android/iOS 기기에서 재현합니다.
- 삭제 표식 보존 기간은 오프라인 기간과 개인정보 보존 정책을 함께 고려해 별도로 정합니다. 서버 설정과 원격 DB 데이터는 이 검증 전에는 변경하지 않습니다.

현재 코드에서는 이 서버 계약이 확인되지 않았으므로 로컬 보존과 반복 충돌 표시를 유지하는 것이 안전합니다. 서버 계약이 정해지면 스키마 변경과 클라이언트 마이그레이션을 각각 작은 커밋으로 구현하고, 계정별 실제 기록을 백업한 테스트 계정으로 검증합니다.
